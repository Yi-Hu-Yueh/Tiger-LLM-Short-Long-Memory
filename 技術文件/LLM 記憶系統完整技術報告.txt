# 第一篇　記憶系統的基本架構

## 1. AgentCore Memory 解決什麼問題

### 1.1 為什麼代理需要記憶

大型語言模型在一次呼叫中，主要依據當次提供的上下文回答。若應用沒有保存並重新提供歷史資訊，下一次互動不會自然擁有前一次的完整背景。使用者就必須重複說明自己的偏好、正在處理的問題，以及已經嘗試過的方法。

AgentCore Memory 把這項需求拆成兩部分：保存原始互動，以及將值得保留的資訊整理為可在後續任務中檢索的記錄。它處理的是應用層的外部記憶，文件所描述的機制不是每次互動後重新訓練模型權重。

對使用者而言，價值可能表現在三種行為：同一段對話不必反覆交代前情、重新開啟對話時仍能延續重要背景，以及代理能利用過往任務經驗改善處理方式。

### 1.2 適用工作負載

文件列出的場景包括客服、任務與工作流程代理、多代理協作，以及需要利用歷史資訊的規劃型應用。這些場景的共同需求，是在不同時間點仍能取得與目前工作有關的狀態或知識。

以下為具體示意：

| 場景 | 需要記住的內容 | 記憶帶來的改變 |
|---|---|---|
| 客服 | 使用者描述的問題、已試過的方法、溝通偏好 | 不再從第一個排除步驟重新問起 |
| 工作流程 | 已完成階段、未完成事項、先前決策 | 下一次互動能接續任務 |
| 程式助手 | 問題情境、工具使用過程、成功與失敗經驗 | 面對相似問題時有可參考的處理方式 |
| 個人助理 | 穩定偏好與先前安排 | 回覆能符合個人需求 |
| 多代理系統 | 經授權共享的歷史資訊 | 不同代理可在共同背景下協作 |

記憶不會自行保證任務正確完成。例如，保存了「已提出退款」不代表退款系統已實際執行。涉及業務狀態時，仍應查詢權威系統確認。

### 1.3 托管服務與應用責任

托管的核心價值是減少保存、擷取、整合與檢索記憶的基礎設施工作。應用仍需決定：哪些互動送入記憶、誰有權讀寫、如何選擇記憶、如何組裝模型上下文，以及如何處理錯誤或過時資訊。

因此，採用服務只是完成記憶系統的一部分。真正的使用體驗取決於資料選擇、身分範圍、策略設定和檢索後的使用方式。

## 2. 七個核心物件與它們的關係

### 2.1 Memory resource：頂層記憶容器

Memory resource 是資源管理單位，包含原始事件與衍生的長期記憶。建立時可以設定名稱、說明、事件保存期限、加密與記憶策略。

一個資源可以服務多個 Actor，也可以配置多種策略。是否拆成多個資源，是應用架構選擇，不應把「一個 Memory」誤認成「一段聊天」或「一個人的唯一記憶檔」。

### 2.2 Actor：記憶與誰有關

Actor 可以是人、另一個代理或發起互動的系統。`actorId` 用來將事件及記憶與特定實體關聯。

設計建議：Actor ID 應由可信任的應用層決定。若讓使用者直接提交任意 ID，就可能把別人的 ID 當成自己的資料範圍。ID 本身只是識別字串，不是身分驗證結果。

### 2.3 Session：哪一次互動

`sessionId` 將同一段互動的事件分組。同一個 Actor 可以有多個 Session：例如第一次詢問訂單、第二次追蹤配送、第三次提出其他問題。

會話識別必須穩定到足以延續同一次互動，也必須在需要區分新會話時更換。若每一則訊息都換 Session，歷史會被切碎；若所有使用者共用同一組識別，則可能造成資料混用。這些是應用實作風險。

### 2.4 Event：原始互動單位

Event 是短期記憶的基本單位，帶有時間戳，建立後內容不可變。它可以保存對話、系統活動、工具使用或其他 payload。單一事件能包含多個 payload 項目，所以事件數與訊息數不必相同。

### 2.5 Strategy：從原始資料產生什麼

記憶策略決定保留哪一類資訊及其處理方式。沒有配置策略時，不會自動從原始事件擷取長期記憶；配置多個策略時，同一批互動可能產生不同用途的記錄。

### 2.6 Memory record：處理後資訊

Memory record 是長期記憶中的記錄，具有識別碼，並儲存在指定命名空間。它保存的是經策略整理的內容，不能假設一定能完整還原原始對話。

### 2.7 Namespace：長期記憶放在哪個邏輯範圍

命名空間使用階層路徑組織記錄，可依策略、Actor、Session 分層。它決定查詢範圍，但還需要授權政策限制呼叫者能使用哪些範圍。

簡化關係如下：一個 Memory resource 包含多個 Actor 的多個 Session；Session 內保存 Event；策略處理 Event 後，將 Memory record 放入命名空間。

## 3. 短期記憶、長期記憶與 RAG

### 3.1 短期記憶的「短期」指功能，不代表揮發性

短期記憶保存原始互動，協助代理掌握近期對話和任務背景。文件明確描述它可以在服務重新啟動後重新載入，因此不能直接等同 RAM 或模型內部的 KV Cache。

應用可以透過列出 Session、列出事件、取得特定事件來找回過去互動。即使資料屬於短期記憶，只要尚在保存期限內，也可能用於接續先前的支援案例。

### 3.2 長期記憶是選擇性整理

長期記憶保留事實、偏好、摘要或經驗等資訊，而不是單純複製所有原始事件。內建流程包括擷取與整合：先辨識有用資訊，再判斷是否新增或與既有記錄結合。情景策略另有反思階段。

它是背景非同步處理。原始事件寫入成功後，長期記錄可能尚未生成；搜尋不到資料不能立刻判定資訊沒有保存價值。

### 3.3 RAG 的角色

RAG 用於取得文件、政策、技術規格等可信來源的內容。長期記憶主要補上使用者背景與歷史互動。兩者可共同提供上下文，但不應混淆來源。

例如：

- 記憶提供「使用者偏好用繁體中文解釋」。
- 近期事件提供「本次已經排除了網路連線問題」。
- RAG 提供「現行產品文件要求的下一步設定」。

設計建議：遇到政策、價格、權限或業務狀態時，應優先查核權威來源，不把過去對話中的陳述直接視為現行規定。RAG 也需要來源與檢索品質管理，不能因為使用 RAG 就保證答案一定正確。

## 4. 控制平面、資料平面與兩條處理路徑

### 4.1 控制平面

控制平面用來管理 Memory 資源及設定，例如建立、更新、查詢資源和策略。在 Boto3 中，文件使用 `bedrock-agentcore-control` client。

典型操作流程為：提交建立要求 → 取得 Memory ID → 查詢狀態 → 等待 `ACTIVE` → 開始資料操作。如果狀態是 `FAILED`，應處理失敗原因，而不是持續寫入測試資料。

### 4.2 資料平面

資料平面負責事件與長期記錄的寫入、讀取、列出、搜尋和刪除。Boto3 使用 `bedrock-agentcore` client。

將兩者分開的工程價值，是能讓日常使用記憶的代理只取得必要資料權限，不必同時具有修改資源設定的能力。

### 4.3 即時互動路徑

應用接收使用者訊息，取得授權範圍內的近期事件與相關長期記憶，組裝上下文，再交給模型回答。對話及工具結果可按照應用規則寫成新事件。

這條路徑直接影響使用者等候時間，因此不宜把所有背景擷取與整合都放在每一次回答的必要前置條件中。這是基於非同步特性提出的設計建議。

### 4.4 背景記憶路徑

事件寫入後，啟用的策略在背景處理資訊。產生的記錄留待之後檢索，必要時再由整合流程處理重複或相關內容。文件說明新見解可能需要一分鐘或更久才能取得，不能將示例中的等待秒數當成保證。

# 第二篇　四種記憶策略與系統提示

## 5. 策略全貌：同一段對話可以產生不同記憶

假設使用者說：「我在 Windows 上執行程式失敗，錯誤出現在安裝套件。以後請先給我精簡步驟，不要一次貼整份程式。」代理嘗試一種方法失敗，再改用另一種方法完成。

這段互動可能具有四種不同價值：

| 策略 | 可保留的資訊方向 |
|---|---|
| 語義記憶 | 使用者使用的環境與明確事實 |
| 偏好記憶 | 使用者偏好精簡、分步的說明方式 |
| 摘要 | 本次問題、嘗試過的方法與完成結果 |
| 情景記憶 | 哪種處理方式失敗、什麼替代方式成功 |

以上是說明分工的自編例子，不保證服務一定逐項產生相同文字。實際結果受到策略、訊息內容、提示與模型處理影響。

策略選擇應對應應用真正的需求。若只需要恢復長篇對話，摘要可能最直接；若目標是跨會話個人化，偏好與語義策略更重要；若要學習工具執行經驗，則應考慮情景策略。

## 6. 語義記憶：如何保存與整合事實

### 6.1 擷取範圍

語義策略用來辨識使用者相關事實與情境知識，例如某個支援問題對應的訂單、使用中的版本或已提到的重要日期。文件描述輸出是可獨立理解的 JSON 事實物件。

預設提示要求以使用者訊息為資訊來源，助理訊息只作輔助背景；不加入外部知識，也不從先前歷史重複擷取。沒有值得保留的資訊時，可以回傳空結果。

### 6.2 整合的三種決定

新增適用於既有記憶沒有涵蓋的新事實；更新適用於可補充已有內容而不改變其意義的資訊；略過適用於重複或沒有新增價值的內容。

預設規則強調保留具體細節與時間。遇到互相矛盾的事實，或不同時間的新事件，指示傾向新增記錄，而不是直接覆蓋。

### 6.3 示意：為什麼矛盾不一定代表要刪除舊資料

以下是本報告的分析案例：

原本記錄為「使用者三月在台北工作」，六月又說「我現在搬到台中」。兩句話可能同時具有歷史價值。如果直接把第一句替換成第二句，就失去搬遷前的資訊；如果把它們毫無時間區分地拼成一句，又可能造成表面矛盾。

因此，應用需要先決定自己的問題：是要知道「現在的位置」，還是要回顧「過去的活動」？前者需要當前狀態判斷，後者需要歷史脈絡。不能期待單一語義整合策略替所有業務問題選擇同一種答案。

### 6.4 實作意義

設計建議是把「記錄存在」和「記錄目前有效」分開思考。對可能改變的資訊，應保留時間與來源，查詢時依任務判斷。涉及權威業務狀態時，仍以業務系統為準。

## 7. 使用者偏好：如何避免把臨時需求當成永久設定

### 7.1 明確偏好與隱含偏好

明確偏好是使用者直接陳述的選擇，例如回覆語言或座位需求。隱含偏好則需要較強訊號，例如重複出現的選擇。預設提示不鼓勵從單次、薄弱線索任意推論。

輸出包含背景、偏好與分類，讓記錄不只是「喜歡什麼」，也能保留為何作出這個判斷的脈絡。

### 7.2 哪些資訊可能被略過

整合規則區分持續偏好與一次性事件、暫時狀態或純個人事實，也要求略過重複、過度猜測及特定不宜保存的內容。

這些是 LLM 的判斷指令，不是完整的資料防洩漏機制。若某種資料依法或依產品政策不得儲存，應在應用處理階段限制，而不是只期待偏好提示自行排除。

### 7.3 自編判斷案例

| 使用者陳述 | 建議如何理解 |
|---|---|
| 「以後都請用繁體中文回答」 | 有明確持續性，可作為偏好候選 |
| 「今天先簡短回答」 | 可能只限本次，不能直接永久化 |
| 「幫我找義大利餐廳」 | 單次任務，未必代表長期喜好 |
| 「我每次聚餐都比較想選義大利菜」 | 有較強持續偏好訊號 |
| 「我今天很累」 | 當下狀態，不是穩定偏好 |

這張表是應用設計示例。若產品需要精確區分「這次」與「以後」，應把範圍寫入策略與評估案例中。

### 7.4 偏好與高優先權規則的區別

記住使用者偏好，不代表這段文字可以覆寫系統規範。偏好記錄應成為受控的個人化資料；涉及工具權限或安全政策時，仍由應用的正式規則決定。

## 8. 摘要：縮短上下文，同時保留會話進展

### 8.1 摘要的單位是 Session

摘要策略整理同一會話中的主題、任務與決策。命名空間必須包含 Session 識別，因為摘要是在會話層級維護。單一 Session 可以產生多個摘要區塊，不必只有一份不斷被覆寫的全文。

輸出採 XML 結構，可以分主題組織內容。應用可列出該會話的摘要區塊，也可對區塊做語義檢索，只取與當前問題相關的部分。

### 8.2 全局摘要與差異摘要

預設系統提示處理兩種層次：精簡的全局重點，以及新輸入相對於既有歷史的詳細增量。全局部分維持主要目標與需求；差異部分避免反覆重述舊細節。

此設計的目的是讓歷史越長時，仍能把新增進展與原有背景分開。它不是對摘要永遠正確或完全無損的承諾。

### 8.3 自編案例：長篇故障排除

一段會話的前半部，使用者已確認網路正常並重新啟動軟體；後半部才找到權限設定有誤。完整逐字稿可能很長，但下一次回答最需要的是：問題目標、已排除項目、最新發現與下一步。

設計建議：摘要可用來引導後續處理，但需要精確引用參數、錯誤訊息或數字時，應回到原始事件核對。摘要是一種壓縮表示，不是所有細節的替代品。

## 9. 情景記憶：把任務過程整理成經驗

### 9.1 什麼是情景

情景是有意義的任務片段，重點包括為何開始、想達成什麼、做了哪些事，以及是否成功。它通常比單句事實更豐富，也比整段逐字稿更有結構。

情景由單一 Session 的互動形成，但可以依設定儲存在不同範圍的命名空間。策略會判斷情景是否完成；沒有完成訊號時，記錄可能較晚生成。文件建議包含工具結果，讓任務結果的分析有依據。

### 9.2 第一階段：逐單位擷取

使用者補充的系統提示附件，把對話回合和結構化 JSON 事件都視為分析單位，並要求逐項處理。它不是只看人與助理的自然語言，也重視系統所記錄的具體活動。

每個單位的分析方向包括：

| 面向 | 要解答的問題 |
|---|---|
| 情境 | 在什麼條件下發生這個動作？ |
| 意圖 | 這一步想達到什麼目的？ |
| 行動 | 執行了哪些操作、用了哪些參數？ |
| 簡要理由 | 依當前資訊，為何採取這個方法？ |
| 行動結果 | 這一步是否達到目的？ |
| 任務完成情形 | 使用者目前的需求是否結束？ |

附件要求輸出保持精簡，並讓分析單位與輸入單位對應。這能減少只總結最後一個回答、忽略中間工具結果的情況。

### 9.3 如何判斷情景結束

附件的判斷方向是：使用者當前需求已明確結束，或開始新問題、轉往其他任務，可視為前一情景結束；若仍在追問目前問題，就尚未結束。沒有下一回合且沒有明確完成訊號，也不能單憑資料暫停就認定已完成。

工程意義：使用者安靜不一定代表任務成功，工具執行完畢也不一定代表使用者的目標已達成。應用若能記錄明確的任務結果，就能提供較完整的分析依據。

### 9.4 第二階段：整段情景整合

附件要求將逐回合資訊整合成一個任務層級描述，包含情境、使用者意圖、是否成功、判斷依據及反思。

這個階段的價值是把「事件先後順序」轉成「任務為什麼成功或失敗」。例如某次工具呼叫成功回傳，不代表整個任務完成；整合時還要觀察回傳結果是否真正符合使用者需求。

### 9.5 自編情景例子

情境：代理需要處理一份中文文件。第一次讀取因編碼不符失敗。代理辨識出原因後，指定適當編碼重新讀取，完成內容整理。

一條有用的情景記錄應保留：任務目標、第一次失敗的表現、採取的修正、修正後的結果，以及適用限制。若只存「成功讀取文件」，就失去了可重用的故障恢復經驗。

相反地，若把當次使用者的私人檔名、完整路徑或敏感內容直接包進跨使用者經驗，可能帶來資料暴露。因此，任務經驗可重用與個人資料保護需要一起考慮。

## 10. 反思：如何從多次經驗產生可重用知識

### 10.1 反思的輸入

附件描述反思階段會結合主要情景、相關情景及既有反思知識。它不是每次把剛發生的事再摘要一次，而是尋找可延續到未來任務的模式。

分析方向包括：哪些工具選擇經常奏效、哪些失敗有共同原因、什麼條件下需要換方法，以及既有知識是否已經涵蓋這項經驗。

### 10.2 新增與更新

若發現的是既有反思沒有涵蓋的概念，就新增；若是相同核心概念的新證據或改進，則更新既有反思並保留其識別。附件也要求控制條目長度，過度擴張時應拆成更具體的知識，而不是讓每條反思無限制累積。

沒有新經驗時可以不產生新反思。這項原則很重要，因為強迫每次生成新內容，容易製造重複或缺乏依據的「教訓」。

### 10.3 反思條目的實際用途

附件中的主要欄位可理解為：

| 欄位 | 使用意義 |
|---|---|
| 操作 | 這是新知識，還是更新已有知識 |
| 識別碼 | 更新時對應哪一條既有反思 |
| 標題 | 讓概念容易辨識 |
| 適用情境 | 什麼任務、問題或觸發條件下應參考 |
| 具體提示 | 建議做什麼、避免什麼，以及原因 |
| 信心分數 | 生成者對可用性的判斷 |

信心分數不是經統計校準的成功率。它可以協助排序或檢視，但不應直接拿來保證正確性。

### 10.4 自編反思示例

一條經驗可以概括為：「當文字檔讀取成功但出現系統性亂碼時，先檢查編碼設定，再判斷原始內容是否損壞。」

這種表述比「上次把某檔案重讀一次就好了」更可重用，因為它包含適用條件和選擇方法的理由。但它仍應基於實際觀察，不應把一次成功擴大成所有檔案的通用規則。

### 10.5 檢索情景與反思的差異

文件描述情景以意圖為索引重點，反思以使用情境為重點。設計查詢時，應描述任務或問題，而不只匹配偶然出現的名詞。

例如「如何處理工具逾時後的恢復」通常比只查「工具 A」更能表達想找的經驗。檢索成功情景後，也可以把其中的主要步驟提供給代理，作為新任務的參考。

### 10.6 跨 Actor 反思的隱私含義

反思可以設定在比情景更廣的範圍，文件特別提醒跨 Actor 分析的隱私影響。若希望使用者記憶彼此隔離，就應把反思範圍限制在適當層級。

另外，附件的 thought 或 reasoning 欄位只是提示要求生成的簡要分析。不能據此推論服務可以取得模型完整、隱藏的內部思考過程。

# 第三篇　策略設定與資料操作

## 11. 三種管理模式的取捨

### 11.1 內建策略

服務負責既定的擷取與整合流程，適合標準需求。應用仍需選擇策略、組織記憶與評估輸出。它減少的是流程實作工作，不會取消資料治理責任。

### 11.2 內建策略加自訂覆寫

應用可以在托管流程內修改指令、選擇 Bedrock 模型。語義與偏好可覆寫擷取及整合；摘要可覆寫整合；情景可覆寫擷取、整合與反思。

輸出格式仍受內建規格約束，不能任意改變架構或重新命名整合操作。`appendToPrompt` 雖有「附加」字面含義，文件實際將它描述為替換指令部分，使用時應提供完整、連貫的規則。

### 11.3 自管策略

自管讓應用自行處理擷取及整合，可選模型、演算法與記錄表示，再利用服務保存及檢索。代價是需要維護自己的處理基礎設施、錯誤恢復與操作順序。

| 決策問題 | 比較適合的模式 |
|---|---|
| 標準事實、偏好或摘要已足夠 | 內建 |
| 只想限定某個業務領域或改用模型 | 內建加覆寫 |
| 要完全自訂記錄表示或合併邏輯 | 自管 |
| 要整合外部處理系統 | 自管 |

這是根據控制範圍整理的選擇指引，不是對所有應用的固定推薦。

## 12. 自訂指令與模型的設定流程

### 12.1 先明確定義要改變的行為

例如旅遊助理只需要航空公司與座位偏好。自訂的目標應是縮小擷取範圍，而不是刪除所有預設規則後只寫一句「記住旅遊偏好」。後者可能讓去重、來源限定與語言規則失去依據。

設計建議：從預設提示出發，逐條決定保留或修改，並記錄修改原因。輸出架構與操作名稱保持不變。

### 12.2 執行角色

使用自訂模型時，服務會代入 `memoryExecutionRoleArn` 在使用者帳戶呼叫模型。角色需要兩部分：信任政策允許服務代入；權限政策允許所需的模型呼叫。

文件示例涵蓋模型呼叫與串流呼叫權限，並示範以來源帳戶和資源條件限制角色使用。正式系統應把允許範圍縮至必要資源。

### 12.3 模型容量與成本

自訂模型呼叫消耗帳戶自己的 Bedrock 容量與配額。模型呼叫若被節流，記憶擷取也可能失敗。因此，不能只觀察前台聊天模型的負載，還要考慮背景記憶模型的使用量。

成本比較至少需要納入記憶操作與儲存、擷取及整合推論，以及自管模式的外部計算與資料傳送。文件的模式成本比較不足以直接計算特定應用的總帳單，本報告不提供未查證的單價。

## 13. 自管流程的五個環節

### 13.1 觸發

可依訊息數、Token 數或會話閒置時間設定觸發條件，並指定歷史上下文範圍。觸發越頻繁通常代表記憶較新，但也增加處理次數；實際平衡需要依工作負載量測。

### 13.2 交付

服務把資料放到 S3，透過 SNS 通知工作資訊。通知提供工作與資源識別，處理器再取得實際 payload。需要會話順序時，文件建議使用 FIFO 主題。

### 13.3 擷取

自訂處理器讀取目前資料與歷史背景，決定哪些內容值得轉成長期記錄。可使用適合的模型或其他處理邏輯。

### 13.4 整合

處理器負責檢查既有記錄、去除重複並解決衝突。這部分不再只由內建流程替應用決定。

### 13.5 寫回

透過批次建立、更新或刪除記錄操作，把處理結果寫回長期記憶。需要附上正確的命名空間與策略資訊，讓後續查詢能找到資料。

### 13.6 自管實作應另外驗證什麼

以下是設計建議：

- 相同工作被重複處理時，不應產生無限重複記錄。
- 某批資料處理到一半失敗時，要能辨識哪些結果已寫入。
- 同一使用者的多個工作同時修改相近資訊時，需要明確的衝突處理。
- S3 中的已處理資料要有適當保存與清理政策。
- 通知失敗、模型失敗與寫回失敗要能分別觀測。

文件以 SQS、Lambda 作為實作示例，也允許使用其他計算平台。範例組合不等於強制架構。

## 14. 建立 Memory：從空容器到可用資源

### 14.1 可選介面

可以使用 AgentCore CLI、AWS 控制台或 SDK 建立。CLI 的角色主要是專案與資源管理；事件讀寫和會話操作則由相關 SDK 處理。

建立時需要考慮名稱與用途、原始事件保存期限、加密方式、是否啟用長期策略，以及命名空間。若沒有策略，仍可保存原始事件。

### 14.2 等待啟用

文件要求資源進入 `ACTIVE` 才開始使用。正式程式應同時處理成功、失敗與等待，不應只有無限迴圈。

設計建議：設定合理的總等待上限，輸出可診斷狀態，並避免在建立失敗後持續產生測試事件。

### 14.3 後續新增策略

可以更新既有資源增加、修改或刪除策略。但新策略只處理啟用後保存的事件，先前對話不會自動被補做長期擷取。

若要處理舊資料，必須另行規劃遷移或自管處理。不能把修改設定當成既有資料自動轉換。

## 15. 短期記憶的四項操作

### 15.1 建立事件

`CreateEvent` 將新事件寫到指定 Memory、Actor 和 Session。payload 是項目列表，可以保存多個對話回合，也有 Blob 類型的支援。事件不可變，修改對話通常需要額外處理，而不是原地改寫事件內容。

文件提供 branch 機制，使用分支名稱與 `rootEventId` 指定分支起點，可用於訊息編輯或探索另一條對話路徑。

### 15.2 取得單一事件

`GetEvent` 以 Memory、Actor、Session 與 Event 識別碼定位原始事件，適合需要確認某個特定訊息或工具結果時使用。

應用需要精確數字或錯誤訊息時，這比只讀摘要更適合，因為可以回到原始內容。

### 15.3 列出事件

`ListEvents` 用於取得指定 Session 的事件，支援分頁與篩選。`includePayloads` 控制是否回傳內容，文件列出預設為 true；`maxResults` 控制每次回傳數量。

設計建議：做完整歷史重建時要處理全部分頁，並確認排序方式；不能假設第一頁就代表整段對話。

### 15.4 刪除事件

`DeleteEvent` 刪除指定原始事件。這與保存期限引起的自動到期不同，而且不會連帶刪除從該事件產生的長期記錄。

如果產品提供「刪除這段對話」功能，應明確定義使用者的預期是只移除逐字紀錄，還是連同衍生記憶一併處理。

### 15.5 分支對產品的意義

以下是設計分析：使用者編輯訊息後，介面可能只顯示新版本，但舊事件仍可能存在於原分支。因此，分支顯示、檢索範圍與刪除規則必須一致。不能把前端畫面隱藏當成資料已移除。

## 16. 長期記憶的操作與讀寫時序

### 16.1 自動產生

策略啟用後，保存符合條件的事件會啟動背景擷取。生成記錄後，才能透過長期查詢讀取。

應用可維持三種不同狀態：事件保存成功、背景處理狀態，以及查詢結果。將它們分開能避免向使用者宣稱「已長期記住」，實際上卻只有原始事件入庫。

### 16.2 直接寫入記錄

文件在自管流程與元資料章節提到批次建立、更新及刪除長期記錄。此路徑適合已處理資料，不必再經過一般事件擷取流程。

直接寫入代表呼叫者承擔內容選擇與正確性。它不是把任意資料丟進去後，服務一定會重新驗證所有業務事實。

### 16.3 列出與搜尋

列出記錄用於瀏覽或核對既有資料；語義搜尋則依查詢找相關內容。兩者用途不同，後者不適合取代需要完整性的清查程序。

### 16.4 刪除記錄

刪除長期記錄可移除過時、不相關或敏感內容。它與原始事件刪除是不同層次，完整資料治理必須同時考慮兩者及背景作業。

# 第四篇　檢索、資料組織與生命週期

## 17. 語義檢索：參數、分數與使用方式

### 17.1 如何描述查詢

`RetrieveMemoryRecords` 用於搜尋長期記錄。查詢需要識別 Memory、指定命名空間範圍，並提供 `searchCriteria`。

| 參數 | 用途 |
|---|---|
| `searchQuery` | 描述想找的資訊，文件列出最多 10,000 字元 |
| `memoryStrategyId` | 可選，用於限制特定策略的結果 |
| `topK` | 最相關結果數量，預設 10、上限 100 |
| `nextToken` | 讀取後續分頁 |

回傳記錄摘要包含相關分數。文件說明分數來自嵌入向量的餘弦相似度，不是百分比匹配，也不是該事實為真的機率。

### 17.2 命中相關，不代表答案已被驗證

以下是設計分析：一條舊記憶與問題高度相似，仍可能已經過時。例如「使用者以前偏好電話聯絡」和「現在要用哪種方式聯絡」十分相關，但不代表偏好從未改變。

因此，檢索結果的處理至少要區分相關性、時間性、來源及權限。向量分數主要回答第一項，不會代替其他判斷。

### 17.3 查詢文字要能表達任務

下面是自編查詢比較：

| 過於含糊 | 較清楚的查詢方向 |
|---|---|
| 「使用者」 | 「這位使用者對回覆語言和詳細程度有什麼偏好」 |
| 「訂單」 | 「之前針對這個配送問題已經嘗試哪些處理方式」 |
| 「工具」 | 「相似任務中，工具逾時後採取了什麼恢復方法」 |

查詢不是越長越好，而是要明確說出需要的資訊。設計建議是根據問題類型選擇策略與範圍，再形成查詢，不要每次對全部記憶進行模糊搜尋。

### 17.4 topK 是上下文成本控制之一

取得更多記錄可能提高涵蓋率，也可能帶來重複、過時或無關內容。應用可以透過測試決定合理結果數，再對回傳內容去重、排序和裁剪。

這些檢索後處理是應用設計，不代表服務自動替所有模型完成最佳上下文選擇。模型可接受的上下文量，也不代表應該把所有可取得資料都放入。

## 18. 命名空間：把記憶分給正確的人與任務

### 18.1 階層設計

文件提供的組織維度包括策略、Actor 和 Session。概念上可形成以下範圍：

- 特定策略下的單一會話。
- 特定策略下同一 Actor 的所有會話。
- 特定策略下所有 Actor。
- 整個 Memory 資源。

越廣的範圍越容易找出跨會話知識，也越需要謹慎授權。摘要通常需要會話粒度；穩定偏好可能需要跨會話使用。

### 18.2 精確範圍與階層範圍

`namespace` 對應精確命名空間；`namespacePath` 用於搜尋某個階層下的記錄。兩者不能只因為字串相似就混用。

文件建議路徑以斜線結尾，降低前綴碰撞的風險。例如對使用者名稱做字串前綴比對時，少了路徑邊界可能誤及另一個名字開頭相同的使用者。

### 18.3 IAM 如何配合

IAM 政策可以依 Actor、Session、命名空間等範圍限制存取。範例示範精確命名空間條件，以及階層路徑的條件。

設計上應把「程式想查哪裡」和「程式有權查哪裡」分開：前者是查詢參數，後者是授權限制。即使程式意外傳入較廣路徑，也不應因此取得超出職責的資料。

### 18.4 自編隔離設計案例

假設應用服務兩家公司，每家公司各有多位使用者。可以先決定是否拆成不同 Memory 資源；若共用資源，則需要穩定且不衝突的 Actor 規則與對應授權範圍。

應避免只在一個全域空間加上 `tenant_id` 欄位，然後要求每支程式「記得篩選」。這種設計一旦某個查詢漏帶條件，就可能暴露其他公司的內容。

同樣地，反思生成也必須遵守資料邊界。檢索限制正確，但背景反思先把不同人的內容混合，仍可能使隔離失去實際意義。

## 19. 元資料：索引、擷取與精確值

### 19.1 文件設定要點

元資料章節區分 `indexedKeys` 與策略 `metadataSchema`：前者控制可篩選欄位，後者控制產生的欄位。記錄支援字串、字串列表及數值；事件元資料使用字串值。篩選先於向量搜尋，最多五條，以 AND 結合。

`LLM_INFERRED` 用於內容推論；`STRICTLY_CONSISTENT` 原樣傳遞已知值，並依值分組擷取與整合。後者最多三個 STRING 欄位、必須建立索引、不支援摘要。

主要限制：索引最多十個、策略架構及記錄元資料各最多二十項。索引新增後不可刪除、不自動回填。批次操作指定策略 ID 時，架構外欄位會被移除。系統建立與更新時間可用於時間篩選。

### 19.2 為什麼「有欄位」和「能篩選」是兩回事

以下是本報告的解釋案例：假設記錄有 `department` 與 `summary_note`。前者需要用來限制搜尋部門，後者只是讓回覆更好理解。兩者都能作為記錄背景，但不必同時占用有限的索引名額。

如果程式寫入了一個欄位，卻沒有完成所需索引設定，就不能假設查詢時可使用它。同樣地，只宣告可索引欄位，卻沒有安排資料值如何進入記錄，也可能得到空結果。

### 19.3 已知值不應交給模型重新猜

假設後端已知某項互動來自帳務部門，卻又要求模型根據文字判斷部門，可能產生不同名稱或分類。這種不必要的推論會降低篩選一致性。

設計建議：由應用掌握的組織資料應走精確值路徑；對話內容才揭露的主題、情緒或需求，才考慮讓模型推論。兩種欄位的可靠性與來源不同，後續也不應同等看待。

### 19.4 架構變更是一項資料遷移問題

新增欄位後，新舊記錄可能具有不同形狀。例如較早的記錄沒有 `department`，新記錄才有。這時若所有查詢突然強制要求該欄位，舊記錄就可能不再出現。

設計建議：在更新前先決定缺值怎麼處理、舊資料是否需要更新，以及新查詢何時啟用。不要把修改設定當成資料已經全部完成遷移。

### 19.5 建議的欄位規劃表

下表是自編的規劃工具，不是服務的固定 schema：

| 問題 | 規劃時要填寫的內容 |
|---|---|
| 為什麼要這個欄位？ | 要改善哪類查詢或業務判斷 |
| 值由誰提供？ | 後端已知、人工輸入或模型推論 |
| 必須精確嗎？ | 是否允許分類上的不確定性 |
| 需要篩選嗎？ | 是否值得使用索引名額 |
| 舊記錄沒有值怎麼辦？ | 保留、補資料或分開查詢 |
| 寫入後如何驗證？ | 列出或取得記錄，核對實際欄位 |

## 20. 過期、刪除與「忘記」的不同層次

### 20.1 原始事件保存期限

文件指出原始事件最多保存 365 天。`eventExpiryDuration` 在事件寫入時決定該事件的到期行為；後續變更設定，只影響之後的新事件。既有事件不能靠延長設定恢復，過期事件亦不能復原。

這個期限不是所有長期記錄的共同 TTL。應用不能以為設定原始事件保存三十天，就代表三十天後所有衍生偏好、摘要和經驗也一起消失。

### 20.2 三種刪除意圖

使用者說「刪除」時，可能指不同事情：

1. 刪除畫面中的某則訊息。
2. 刪除後端原始事件。
3. 刪除從這些內容產生的長期資訊與外部副本。

文件提供的是不同資源與記錄的操作，產品需要自行把它們對應到清楚的使用者行為。

### 20.3 自編案例：使用者撤回地址資訊

使用者曾在對話中提供地址，後來要求移除。可能涉及原始訊息、語義事實、會話摘要、相關情景，以及已同步到外部的資料。

如果只刪原始訊息，摘要仍可能包含地址；如果只刪某條事實，另一條記錄仍可能提到相同資訊。這說明刪除需求不能只靠單一已知記錄 ID 完成。

### 20.4 建議的跨層刪除流程

以下屬於治理設計建議：

- 定位使用者、會話與相關命名空間。
- 盤點原始事件與衍生記錄。
- 處理仍在進行或等待重試的背景作業。
- 刪除必要資料並同步通知外部儲存或消費者。
- 等候相關非同步工作收斂後，再次核對。
- 保留不含被刪敏感內容的作業結果，供服務維運確認。

本次文件沒有提供一個涵蓋所有上述層次的一鍵「完全忘記」流程，因此不應把這段建議當成既有 API 名稱或服務保證。

## 21. 失敗擷取的診斷與重新處理

### 21.1 官方提供的機制

長期擷取失敗後，服務會嘗試處理；持續失敗時，可透過 `ListMemoryExtractionJobs` 查看工作及原因，再用 `StartMemoryExtractionJobs` 重新啟動。文件建議監控 `FailedExtraction`。

| 失敗類別 | 對應處理方向 |
|---|---|
| 長期擷取 Token 配額超限 | 調整負載或申請足夠配額 |
| 自訂模型存取被拒 | 檢查執行角色與信任、模型權限 |
| 模型節流 | 檢查模型 TPM／RPM 容量 |
| 模型逾時 | 檢查模型選擇與處理耗時 |
| 模型不存在或驗證錯誤 | 核對模型 ID 與設定 |
| 暫時性模型／服務錯誤 | 適當等待後重新處理 |

### 21.2 不同故障階段要分開

以下是建議的排查順序：

第一步確認原始事件真的存在。第二步確認策略在寫入時已啟用。第三步檢查擷取工作是否完成或失敗。第四步確認生成記錄的命名空間。最後才調整語義查詢。

若順序反過來，可能在資料根本沒有產生時，不斷修改檢索文字或 topK，卻無法解決問題。

### 21.3 重試前應先處理原因

權限錯誤不會因重試次數增加而消失；配額不足也可能讓同一工作再次失敗。設計建議是把失敗分類後分別處理，並限制重試行為，避免背景工作越積越多。

# 第五篇　串流、跨帳戶與框架整合

## 22. 記憶記錄串流

### 22.1 串流的是記錄異動

Memory record streaming 將記錄新增、更新及刪除通知推送到 Kinesis。它讓下游知道記憶資料改變，並不是模型一邊生成回答、一邊顯示 Token 的回覆串流。

可選擇只送元資料或包含記錄正文；刪除通知只有 Memory 與記錄識別。設定成功後會傳送啟用確認事件。

### 22.2 事件來源

記錄可由背景擷取或直接批次建立產生；直接批次修改對應更新；人工刪除與部分整合流程可產生刪除通知。下游不能假設每次內容整合只會出現一個更新事件。

### 22.3 設定流程

建立 Kinesis stream、準備消費者、設定服務可代入的角色與寫入權限，再於 Memory 設定傳送資源。若使用加密 stream，還需要相應金鑰權限。

文件提供成功、失敗及使用者設定錯誤的傳送指標，並在不可重試失敗時提供日誌。

### 22.4 下游同步設計

以下為工程建議：

- 消費者以記錄識別維護資料，不只按文字比對。
- 處理重複執行時，結果不應被重複累加。
- 同步新增也必須同步刪除，才能維持資料治理一致。
- 需要完整內容時，在正文隨通知傳送與另行讀取之間選擇。
- 重要場景可定期對照主記憶資料，辨識下游落差。

文件未在本次範圍中完整交代所有交付順序與一致性保證，因此不能自行宣稱串流必然為恰好一次或全域有序。

## 23. 跨帳戶存取的兩種架構

### 23.1 其他帳戶操作 Memory

帳戶 A 持有 Memory，帳戶 B 的代理要讀寫時，A 為資源附加允許政策，B 的呼叫者也需要身分權限。兩邊都允許、且沒有明確拒絕時才能成功。呼叫時使用完整 Memory ARN。

### 23.2 將資料傳送到其他帳戶

另一種情況是 Memory 位於 A，但 S3、SNS 或 Kinesis 位於 B。這需要 A 的執行角色有權存取目標，B 的資源政策也允許該角色。

這與讓 B 的代理直接讀取 A 的 Memory 是不同授權路徑，不能只設定其中一邊就期待全部成立。

### 23.3 權限管理建議

文件建議限定具體角色、採最小權限、區分讀寫者並記錄跨帳戶活動。撤除資源政策前，先確認是否有依賴它的工作負載。

工程上可進一步把資源擁有者、資料讀取者、資料產生者與串流消費者列成表，明確定義各自可執行的操作。如此比對所有角色給相同權限更容易維護。

## 24. AWS SDK：直接操作的控制力

### 24.1 直接 API 的優點

Boto3 範例以控制平面建立資源，再以資料平面保存對話。程式能明確管理策略、Actor、Session、事件時間與 payload，適合需要細緻控制的應用。

### 24.2 要自行處理的事項

直接呼叫也意味著程式需要自行處理資源狀態、例外、分頁和結果檢查。文件中的簡短範例可能只展示主要路徑，沒有包含所有正式環境的故障處理。

設計建議：把這些公共處理封裝在應用自己的記憶存取層，讓各個代理不必重複實作，但保留明確的身分與範圍參數。

### 24.3 範例的真正閱讀方式

應注意範例示範的是哪一層：建立 Memory、送入原始資料、等待啟用，還是檢索長期結果。不要把只演示寫入的程式當成完整的個人化代理。

## 25. AgentCore Python SDK：較高層的封裝

### 25.1 常見操作

文件使用 `MemoryClient` 提供建立記憶、建立並等待、加入訊息及檢索等較方便的方法，也使用會話管理類別整理回合操作。

這可減少直接組裝 payload 的工作，但 helper 的方法名稱、參數命名與底層 API 不一定完全相同。

### 25.2 使用時應確認什麼

設計建議：固定 SDK 版本，檢查實際回傳結果和錯誤傳遞方式。尤其要確認等待 helper 等的是資源啟用，還是長期擷取完成；兩者是不同時間點。

### 25.3 適用選擇

若需求主要是常見的對話保存與檢索，較高層 SDK 能使程式更清楚；若要精確控制新功能參數或完整資料操作，則可能仍需要直接 API。兩者可以依功能混合，但應保持統一的資料識別與授權邊界。

## 26. LangChain 與 LangGraph：checkpoint 與長期知識分工

### 26.1 AgentCoreMemorySaver

Saver 用來保存和載入 checkpoint，包括訊息、圖執行狀態及其他脈絡。整合利用短期記憶的 Blob 支援來持久保存狀態。

配置時需要 Memory 資源，呼叫代理時提供 `actor_id` 和 `thread_id`；後者對應 Session。

### 26.2 AgentCoreMemoryStore

Store 用於保存供長期擷取的訊息及搜尋記憶。文件示範在模型前後的 hook 選擇訊息保存，也可在呼叫模型前搜尋記憶，或提供可按需使用的搜尋工具。

因此，Saver 和 Store 不是兩個可互換的名稱：前者偏向執行狀態恢復，後者連接長期資訊的產生與使用。

### 26.3 常見誤判

同一個 thread 再次回答時記得上句話，可能只是 checkpoint 起作用。若要證明長期記憶有效，應保留同一 Actor、換新的 Session，並確認結果來自已生成的長期記錄。

這是建議的驗收方式，不是要求所有應用都必須在每次回答做長期搜尋。

## 27. Strands：會話管理與批次緩衝

### 27.1 基本整合

Strands 範例透過 `AgentCoreMemoryConfig` 與 `AgentCoreMemorySessionManager` 把 Memory、Actor、Session 設定交給代理的會話管理器。這讓記憶操作與代理互動整合得更直接。

### 27.2 批次的收益與代價

`batch_size > 1` 時，訊息先在程式內緩衝，達到門檻後才送出，以減少請求數。文件要求使用 context manager 或在結束時呼叫 `close()`，確保不足一批的訊息也被送出。

如果沒有完成這一步，尾端訊息可能遺失。對使用者而言，代理似乎正常回答，但稍後恢復會話時，最後幾句可能不存在。

### 27.3 應如何測試

設計建議至少測試三種狀況：訊息量剛好達批次門檻、未達門檻就正常結束，以及程式發生例外後的清理路徑。不能只測長時間對話，因為它通常自然達到門檻，反而掩蓋尾端漏送問題。

# 第六篇　安全、維運與端到端應用

## 28. 加密、權限與記憶污染

### 28.1 靜態加密

文件說明記憶資料預設有靜態加密，可選擇客戶管理的 KMS 金鑰以取得額外控制。使用自訂金鑰時，需要角色與金鑰權限相互配合。

此外，事件元資料的說明提醒它不以客戶管理金鑰加密，不應放入敏感內容。不能因為資源設定了 CMK，就假設每個欄位和所有下游副本都採用同樣方式。

### 28.2 加密不會驗證事實

加密能保護資料保存，不會判斷記憶內容是否正確。若合法寫入者提交錯誤資訊，服務仍可能把它當成待處理內容。

記憶污染指錯誤或有害資訊進入長期記憶，影響之後的回覆。提示注入則可能利用輸入內容操控擷取或後續模型行為。文件明確把應用輸入驗證及防範此類問題列為客戶責任。

### 28.3 記憶應作為資料使用

以下為設計建議：

- 不把記憶正文放入具有最高優先權的規則位置。
- 不讓記憶中的自然語言自行授予工具或帳戶權限。
- 對外部來源與使用者陳述保留來源區別。
- 涉及重要操作時，重新檢查現行授權與業務狀態。
- 寫入前與使用前都考慮內容檢查，並做對抗測試。

Guardrails 可作為防護的一部分，但不應被當成所有污染都能被攔截的保證。

### 28.4 最小權限

日常回答問題的角色可能只需要讀取特定記憶；建立資料的角色需要必要寫入權限；維運角色才可能需要修改資源或刪除。把權限依工作分開，能減少單一錯誤的影響範圍。

## 29. 可觀測性：看見流程，也要看見品質

### 29.1 文件提供的觀測方向

CloudWatch 可觀察資料操作的呼叫次數、延遲、錯誤，以及擷取和整合的執行情形與記錄數量。啟用日誌傳送後，可取得背景處理的錯誤資訊。

串流另有傳送成功、失敗和設定錯誤指標；擷取失敗有專門的工作查詢與重試機制。

### 29.2 服務健康不等於記憶有用

以下為工程分析：所有 API 都成功，仍可能把短暫要求存成長期偏好，或搜尋到高度相關但過期的記錄。因此，必須同時評估「流程有沒有運作」與「產生的資訊對任務是否有幫助」。

建議把評估分成四層：

| 層次 | 評估問題 |
|---|---|
| 保存 | 原始資料是否完整進入正確範圍 |
| 生成 | 該保留的有沒有保留，不該保留的有沒有略過 |
| 檢索 | 當前任務能否找到正確且有權使用的內容 |
| 使用 | 回答是否因記憶而更準確，是否誤用過時資訊 |

### 29.3 建議指標

可自行建立跨 Session 找回成功率、錯誤偏好比例、刪除後再次出現比例、錯範圍命中次數，以及從事件寫入到記錄可檢索的時間分布。

這些是應用品質指標，不代表全部都由服務直接提供。評估時應使用預先定義的案例與預期結果，避免只看幾次看似合理的回覆。

## 30. 客服代理端到端案例

本章將文件中的客服流程重新整理成可理解的應用時序；個別延伸判斷屬於本報告的設計分析。

### 30.1 建立資源

先建立 Memory，配置會話摘要與使用者偏好策略，等待可用。摘要依 Actor 與 Session 保存，偏好則按 Actor 跨會話組織。

### 30.2 開始互動

客服系統辨識回訪使用者，建立本次支援 Session。使用者說明訂單延遲，同時表達未來偏好的配送方式。

### 30.3 保存原始對話

使用者與助理訊息進入事件。應用可以逐次或批次寫入，但需要確保必要內容、角色與識別都正確。

### 30.4 產生不同長期記錄

摘要整理本次問題及處理進展；偏好策略整理持續的配送選擇。這兩種結果來自同一段互動，但回答不同需求。

### 30.5 本次互動如何使用短期資料

在對話尚未結束時，代理可載入本次事件，知道使用者剛才說過什麼，不必等長期記錄才理解訂單問題。

### 30.6 新會話如何使用長期資料

下次互動建立新的 Session，但維持同一 Actor。代理在正確範圍查詢配送偏好或先前問題摘要，再把相關內容用於回覆。

設計上仍應確認偏好是否適用於本次情況。偏好是個人化背景，不代表可以覆寫現在的配送限制或業務規則。

### 30.7 哪些訊號才算整體成功

成功不只是助理回答「我記住了」。應確認事件存在、長期記錄已生成、換 Session 後仍可檢索，而且另一位使用者無法取得這些資訊。

## 31. 導入計畫：每個階段解決一類問題

### 階段一：完成可恢復的事件保存

先不追求所有記憶功能，驗證 Actor 與 Session 正確、事件完整、重新啟動後可載入，以及授權範圍符合預期。

### 階段二：加入最小必要策略

依需求選擇事實、偏好或摘要，建立明確輸入與預期輸出案例。先測單一策略，再評估多策略是否帶來重複、成本或檢索干擾。

### 階段三：把檢索接回回答

按照使用者身分與任務選擇範圍，限制上下文數量，區分近期事件、長期記憶與外部知識。這時才算讓記憶真正參與代理決策。

### 階段四：加入治理與失敗恢復

驗證刪除、過期、背景失敗及資料架構變更。對需要經驗學習的工作，再加入情景和反思，並確認不會跨出資料授權範圍。

### 階段五：必要時自訂或自管

只有當已知需求無法由內建設定滿足時，再擴大控制權。自訂前先說清楚希望改善哪個量測結果，避免只是因為「可以改提示」就改動整套流程。

## 32. 驗收測試矩陣

以下是本報告提出的實作驗收建議。

| 測試 | 輸入或情境 | 應確認的事項 |
|---|---|---|
| 同會話連續性 | 多輪訊息 | 能正確理解前文 |
| 重新啟動 | 重建代理程式 | 仍可載入已保存資料 |
| 跨會話個人化 | 同 Actor、新 Session | 找回適用偏好或事實 |
| 跨使用者隔離 | 不同 Actor、相似問題 | 不互相取得記憶 |
| 明確偏好 | 使用者說「以後都……」 | 保存範圍與產品語義一致 |
| 暫時需求 | 使用者說「今天先……」 | 不無條件永久化 |
| 重複資訊 | 同一內容多次出現 | 觀察是否產生過多冗餘 |
| 衝突事實 | 不同時間的相反陳述 | 不失去必要時間脈絡 |
| 新增策略 | 啟用前後分別寫事件 | 驗證不自動回填 |
| 修改期限 | 舊事件與新事件 | 各自保留應有到期行為 |
| 原始事件刪除 | 刪除某事件 | 不誤以為衍生記憶已刪 |
| 長期記錄刪除 | 刪除指定記錄 | 查詢與下游符合預期 |
| 權限錯誤 | 自訂模型角色不足 | 能觀測並定位原因 |
| 配額超限 | 背景處理失敗 | 修正後可重新處理 |
| 元資料變更 | 新欄位與舊資料 | 查詢不意外遺漏必要資料 |
| 批次結束 | 未滿 batch_size | 緩衝資料正常送出 |
| 情景未完成 | 使用者仍追問 | 不只憑停頓判定成功 |
| 反思範圍 | 相似任務、不同 Actor | 不產生未授權跨人混合 |
| 提示注入 | 記憶含操控性文字 | 不升格為系統指令 |
| JSON payload | 結構化輸入 | 依實際版本驗證擷取支援 |

## 33. 與前面錄音內容的技術對照

錄音談的是一般記憶系統設計思路。本報告閱讀的則是特定服務行為，兩者需要分開。

### 33.1 RAM、Redis、KV Cache 的比喻

短期記憶可類比工作中的即時背景，但 AgentCore 保存的是可持久取回的事件。本次文件沒有證實其底層使用 Redis，也不應將外部事件保存與模型推論的 KV Cache 當成同一層技術。

### 33.2 向量庫、圖庫與關聯庫的組合

一般系統可以選擇混合不同資料庫，但本次文件主要揭露的是記錄、策略、命名空間與語義檢索介面。不能據此寫成 AWS 內部必然使用某個三庫組合。

### 33.3 去重門檻與時間衰減

錄音提到固定相似度門檻、時間權重衰減與按訪問頻率淘汰。這些可作為自管設計的討論方向，本次文件並沒有把它們列成通用內建保證。

### 33.4 衝突資訊直接覆寫

語義預設提示對矛盾資訊採新增處理方向，這與「最新事實一定直接覆寫舊事實」不同。要維護唯一目前狀態的應用，需另有明確規則。

### 33.5 背景反思

錄音的背景整理概念與非同步處理、情景反思相近。但不能因此推論所有策略都在夜間執行，或所有應用都必須使用同一套定時管線。

## 34. 文件差異與不能過度推論的地方

### 34.1 JSON 事件的支援範圍

建立事件頁仍說只有對話資料進入長期記憶；使用者提供的情景提示則把 JSON 事件列為分析單位。這可能涉及文件更新、語言版本或策略差異，本次無法確認所有路徑的統一行為。

因此，報告保留這項差異，不把提示描述直接改寫成「任何 Blob 都能由所有策略擷取」的產品結論。實作應使用實際策略、區域與 SDK 做驗證。

### 34.2 範例中的名稱與格式

部分頁面出現 helper 名稱與 API 名稱混用、Actor 路徑單複數不同或示例斜線不一致。閱讀時應理解概念，但實作不能只憑人工翻譯文字拼參數。

同樣地，範例模型 ID、等待秒數與搜尋門檻，只能當作示例；它們不代表目前每個帳戶都有相同模型可用，也不代表適合你的資料。

### 34.3 機器翻譯造成的誤導

部分中文頁把 LLM 翻為「法學碩士」、Actor 翻為「演員」、Memory 翻為「內存」。本報告依技術語境使用「大型語言模型」、「互動實體」與「記憶」，避免把翻譯錯誤帶入概念。

### 34.4 未公開的不替它下結論

文件沒有完整揭露底層資料庫組合、所有一致性保證、每種策略的內部去重門檻及各類操作的固定延遲。本報告不以推測填補這些空白。

## 35. 最終結論

AgentCore Memory 可以把原始互動整理成事實、偏好、摘要與經驗，並提供跨會話檢索、資料組織、異動串流及框架整合能力。它降低了記憶處理管線的建置工作，但代理是否可靠，仍取決於應用如何保存、授權、取用、修正與刪除資料。

一個完整設計應能回答以下問題：

1. 每條資料與誰有關，來自哪一次互動？
2. 為什麼值得長期保存，應交給哪種策略？
3. 現在需要它的任務是什麼，呼叫者是否有權使用？
4. 它與新資訊矛盾時，應保留歷史還是維護目前狀態？
5. 處理失敗或資料過期時，系統如何發現？
6. 使用者要求刪除時，原始資料、衍生記錄與外部副本是否都納入？

這些問題有明確答案後，記憶才能穩定改善代理的連續性與個人化。單純增加保存量、啟用全部策略，或把更多檢索結果塞進模型上下文，都不能取代這些設計。

# 附錄 C　設定與限制補充

## C.1 元資料篩選運算

文件將篩選表示為左側欄位、運算子與右側值。可用運算方向如下：

| 資料 | 運算方向 |
|---|---|
| 字串、數值 | 相等 |
| 字串列表 | 包含指定成員 |
| 各類欄位 | 存在、不存在 |
| 數值 | 大於、大於等於、小於、小於等於 |
| 系統時間 | 之前、之後 |

時間篩選使用 UTC。事件篩選的支援較少，文件列出存在、不存在與字串相等，不能把長期記錄的全部運算能力直接套用到事件。

## C.2 欄位驗證

模型推論欄位可以限制允許值，避免同一分類出現不同拼字。文件列出的允許值集合最多十個；列表驗證的最大項目數可設一至五。數值可設上下界。

設計建議：分類用穩定的機器值，顯示名稱再由應用轉譯。例如，供搜尋的分類不要隨介面語言改變，否則中文和英文互動可能產生難以一致篩選的值。

## C.3 命名空間模板的閱讀方式

模板中的 `{actorId}`、`{sessionId}` 與 `{memoryStrategyId}` 是由系統資料代入的變數；其餘路徑片段則是組織方式的一部分。寫入端和查詢端必須使用相同規則。

設計建議：集中管理模板，不要讓多支程式各自拼出略有差異的路徑。建立資源後，先查看實際生成記錄的位置，再接入正式查詢。

## C.4 策略調整前的檢查表

| 變更 | 調整前要問的問題 |
|---|---|
| 新增策略 | 新資料何時開始處理？舊資料是否另行遷移？ |
| 改提示 | 是否仍保留來源限定、整合規則與固定輸出格式？ |
| 改模型 | 執行角色、可用性與容量是否足夠？ |
| 改命名空間 | 查詢端與權限設定是否同步？ |
| 改欄位架構 | 舊記錄缺值如何處理？ |
| 改精確值分組 | 前後生成的資料會否落入不同整合範圍？ |
| 改保存期限 | 是否清楚只影響之後寫入的事件？ |
| 啟用串流正文 | 下游是否需要接收和保護完整內容？ |

上述問題是變更管理建議，不能將「設定 API 成功」當成整個資料流程都已驗證。

# 附錄 D　以一筆資訊追蹤整個系統

為了把前述章節連起來，以下以「使用者偏好精簡的繁體中文回覆」示範完整路徑。

**第一站：接收。** 應用先知道是誰說的、屬於哪一段會話，以及這句話是持續偏好還是當次需求。若身分不明，後續即使分類再精確，也可能把記憶歸給錯的人。

**第二站：原始保存。** 將訊息作為事件寫入。此刻能確認的是原始內容被接受，不是長期偏好已生成。

**第三站：策略處理。** 偏好策略判斷其持續性；如果只是「這次簡短一點」，結果可能與「以後都簡短一點」不同。這也是應用應準備評估案例的原因。

**第四站：整合。** 若既有記憶已表達相同偏好，理想上不必不斷新增相同資訊；若出現更具體條件，例如技術問題可詳細、一般問題簡短，則需要保留條件，不能把它壓成互相矛盾的兩個標籤。

**第五站：組織。** 記錄存入適當的 Actor 範圍。若誤存全域路徑，之後其他使用者可能受到不屬於自己的偏好影響。

**第六站：檢索。** 新會話開始後，應用在授權範圍內找與回覆方式相關的記錄。若未執行檢索，偏好即使已保存也不會自動出現在每次模型呼叫中。

**第七站：使用。** 應用將偏好作為個人化背景，同時保留目前使用者指令。如果使用者這次明確要求詳盡報告，舊的簡短偏好不應機械式阻止完成本次需求。

**第八站：修正或移除。** 使用者更改偏好時，應按產品規則處理更新；要求刪除時，則需要考慮原始事件和衍生記錄。這一步完成後，再檢查後續互動是否還會取出已撤回內容。

這個自編案例說明：保存、整合、檢索與遵循偏好是不同能力。任何一站缺失，都可能造成「系統說記住了，但實際行為不對」。
